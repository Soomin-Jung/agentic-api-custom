# v0.9.0-custom: Responses 오류 계약과 운영 전환

Baseline: upstream `v0.9.0` (`8038abf`). Custom branch: `release/v0.9.0-custom`.
기존 `release/v0.5.0-custom`은 기존 이미지 재현 및 롤백 소스로 보존한다.
Cargo/Python 버전은 upstream `0.9.0`을 유지한다. 커스텀 빌드는 **이미지 태그 + Git SHA**로 식별한다.

## AS-IS / TO-BE

| 경계 | AS-IS: vanilla 0.9.0 | TO-BE: 0.9.0-custom |
| --- | --- | --- |
| 초기 upstream POST | lazy stream을 먼저 반환하여 초기 400도 outer 200 SSE가 될 수 있음 | 첫 POST의 성공 상태·헤더를 확인한 뒤 stream을 반환. 초기 400/404/429/5xx는 실제 HTTP 오류 |
| 첫 토큰 대기 | upstream 연결조차 stream poll 이후 시작 | 상태·헤더만 기다림. 첫 body chunk/TTFT는 stream 반환 조건이 아님 |
| 후속 inference | 이미 시작된 stream에서 오류 전달 | 같은 계약 유지. `downstream_stream_error` WARN 로그에 round/status/category 기록 |
| EOF / `[DONE]` | live lenient 경로는 미완성 response를 성공으로 보정할 수 있음 | 명시적인 `response.completed` / `response.failed` / `response.incomplete` 없이 종료하면 오류 |
| generic `type:error` / malformed data | 처리 정책에 따라 무시하거나 전달 후 성공할 수 있음 | 기존 normalization/accumulator 경로에서 실패. 완료 이벤트를 만들어 성공으로 저장하지 않음 |
| 실패·미완료 terminal | Rust `Err`가 없는 경우 운영 로그에서 놓칠 수 있음 | `downstream_terminal_failure` WARN |
| pass-through (`store:false`) | SSE body 오류를 별도 관찰하지 않음 | `proxy_stream_*` WARN. upstream bytes/status를 수정하지 않음 |
| 취소 | lazy stream에서 worker 시작 | bootstrap 중 취소, 반환된 stream의 미사용/drop 모두 worker abort guard가 소유 |

기존 custom timeout 및 upstream error header 패치는 upstream 구현을 사용한다.
새 구현은 `AgentPipeline` → `RoundIngestion` → `ResponseAccumulator` 단일 ingestion 경로를 사용한다.
WebSocket shutdown guard는 executor 실행 시작 전에 확인한다. 이미 upstream 호출이 시작된 요청은
종료 시 drain하고, 대기열의 새 요청은 기존 admission 정책에 따라 버린다.

요청별 bounded event channel 및 event byte limit은 유지한다. 새 unbounded channel은 없다.
초기 commit gate는 ready/release 두 개의 payload 없는 oneshot만 사용한다.

## 오류 로그 설정

추가 기능은 기본 활성화다. 배포 환경에서 최소한 다음 필터를 사용한다.

```text
RUST_LOG=info,agentic_server=info
STREAMING_CHUNK_TIMEOUT_S=0
AGENTIC_LOG_ERROR_DETAILS=false
```

`STREAMING_CHUNK_TIMEOUT_S=0`은 기존 장시간 prefill 운영 설정 예시다. upstream에서 정식 지원하며,
다른 프록시/네트워크 타임아웃까지 해제하지 않는다. 정상적인 종료/실패 로그에는 `info` 필터면 충분하다.
경계 DEBUG까지 필요하면 `RUST_LOG=info,agentic_server=debug`를 사용한다.

| phase | 의미 | 주요 필드 |
| --- | --- | --- |
| `request_error_before_stream` | stream 반환 전 초기 요청/준비 실패 | `response_id`, `model`, `inference_round`, `upstream_status`, `error_type`, `error_code`, `reason_category` |
| `downstream_stream_prepared` (DEBUG) | 초기 upstream 성공. stream을 노출할 준비 완료 | `response_id`, `model` |
| `downstream_stream_started` (DEBUG) | caller가 stream body 소비 시작 | `response_id`, `model` |
| `downstream_stream_error` | 초기 upstream body 또는 후속 inference/tool 처리 실패 | 위 오류 필드 + 가능한 `upstream_request_id`, `error_bytes` |
| `downstream_terminal_failure` | 명시적 failed/error/incomplete terminal | `response_id`, `model`, `inference_round`, `terminal_status`, `reason_category` |
| `downstream_terminal_serialization_error` | 최종 이벤트 크기/직렬화 실패 | 오류 필드 |
| `downstream_persistence_error` | 완료 이벤트 노출 전 저장 실패 | 오류 필드 |
| `downstream_stream_task_error` | 노출된 stream의 worker 실패 | 오류 필드 |
| `proxy_stream_error_event` | pass-through generic error event | `request_id`, 가능한 upstream `response_id`, `model`, `downstream_http_status`, `reason_category` |
| `proxy_stream_terminal_failure` | pass-through failed/incomplete | 같은 필드 |
| `proxy_stream_read_error` | pass-through body 읽기 실패 | 같은 필드 |
| `proxy_stream_missing_terminal` | 인식한 Responses lifecycle이 terminal 없이 EOF | 같은 필드 |
| `proxy_stream_observation_limit` | 64KiB를 초과한 line 관찰을 건너뜀 | 같은 필드. 해당 line 이후 관찰 재개 |

`inference_round`는 **0부터 시작**한다. 아직 inference에 진입하지 않았거나 terminal 저장 단계라 round가
없는 경우 그 필드는 생략된다. `upstream_status`는 실제 non-2xx HTTP 응답을 받은 경우에만 존재한다.
HTTP 200 body의 `type:error`에서 status 숫자를 추측하지 않는다.

예: 후속 round에서 vLLM이 context 초과 400을 반환하면 다음과 같이 기록한다.

```text
WARN agentic_server: Responses request failed phase="downstream_stream_error" response_id="resp_..." model="Qwen3.8-27B" inference_round=1 upstream_status=400 reason_category="context_length_exceeded"
```

위 예시는 필드 의미를 설명하며, 실제 필드 순서·따옴표는 tracing formatter에 따라 다르다.
`response_id`로 SSE response 이벤트와 서버 로그를 연결할 수 있다.
0.9.0의 `agentic.execute` / inference-round / HTTP-client span 및 trace context propagation을 그대로 사용한다.
기존 custom의 `responses.execute` span은 추가하지 않는다. stream 반환 전 실패도 execution failure로 기록한다.
오류 event 자체의 OTLP export는 upstream subscriber 정책을 따른다. WARN은 stdout 로그로 수집한다.

원문이 필요하면 `AGENTIC_LOG_ERROR_DETAILS=true`로 **프로세스를 재시작**한다. 활성 여부는 프로세스에서
한 번 읽는다. `error_detail`은 UTF-8 경계를 보존한 최대 1024 bytes이며 제어 문자를 공백으로 바꾼다.
오류 원문은 backend가 요청 내용을 포함할 수 있으므로 기본값은 false다. 기본 로그에는 prompt,
tool arguments/output, auth 값을 추가하지 않는다. 기존 upstream 로그 정책은 별개다.

pass-through 관찰은 request당 한 line을 최대 64KiB 보관한다. 큰 이벤트는 관찰만 건너뛰고 원문을 전달한다.
따라서 모든 provider-specific body를 완전히 검증한다는 의미는 아니다. executor live 경로는 기존 설정된
upstream line/event 크기 제한으로 검증한다. HTTP와 WebSocket의 executor가 이 core 경로를 공유한다.

## 0.8.0-custom에서 재사용 / 변경한 부분

| 항목 | 0.9.0-custom 처리 |
| --- | --- |
| 초기 handshake, 오류 WARN, terminal 누락 검증, pass-through 관찰 | 기존 custom 패치 재사용 |
| 요청/실행 tracing 및 upstream trace header | 0.9.0 공식 구현 재사용; 중복 custom span 제거 |
| 저장 Responses GET, store:false continuation, prompt_cache_key, Conversations API | 0.9.0 공식 구현 유지 |
| code interpreter done-only item ID 보정 | live accumulator 분리에도 공식 보정 유지 |
| agent round | 0.9.0 AgentTurn 소유 지점에서 custom 로그 round 설정 |
| HTTP multi-agent | coordinator admission 후 stream 반환; upstream 실패는 SSE 내부 오류 |

단일-agent의 초기 HTTP 오류 계약을 multi-agent에 확대하지 않는다. multi-agent는 여러 독립적인
upstream 호출 및 public collaboration event를 갖기 때문에, coordinator 검증이 끝난 후 gate를 연다.
첫/후속 agent inference 오류는 0.9.0의 in-band 계약을 유지한다. 복원된 tree continuation에도 동일하다.
초기 coordinator 준비 실패는 stream 반환 전 오류다. 기존 multi-agent cancellation token과 task join,
ExecutionSpan/InstrumentedStream의 poll·drop lifecycle을 유지한다.

## HTTP 계약

- 단일-agent HTTP stream 노출 전: 로컬 validation/rehydration/tool 준비 실패, 초기 upstream non-2xx/연결 실패는 실제 HTTP 오류.
- HTTP stream 노출 후: body 읽기, tool execution, round 1+, persistence 실패는 SSE 오류. 이미 전송한 HTTP 200은 변경 불가.
- 명시적 failed/incomplete는 해당 terminal event를 유지하며 WARN으로 기록.
- 요청을 모두 Agentic API로 라우팅해도 `store:false`이며 in-process 기능이 없으면 내부 pass-through 경로가 선택될 수 있다.
  이 경로에도 위 오류 관찰 로그를 적용한다. 모든 요청을 강제로 executor로 바꾸지는 않는다.

## 이미지 빌드 및 배포

```bash
git checkout release/v0.9.0-custom
custom_revision=$(git rev-parse HEAD)
docker build --build-arg OCI_SOURCE=https://github.com/Soomin-Jung/agentic-api-custom \
  --build-arg OCI_VERSION=0.9.0-custom \
  --build-arg OCI_REVISION="$custom_revision" \
  -t YOUR_REGISTRY/agentic-api:0.9.0-custom .
```

빌드는 upstream `Dockerfile`, `Cargo.lock`, `docker-entrypoint.sh`를 사용한다. 실제 registry push, 운영
ConfigMap/Deployment 변경은 이 PR의 검증과 별도다. 운영에서는 mutable tag 대신 검증된 image digest를 고정한다.

## PostgreSQL 전환

일반적인 0.5/0.9 혼합 rolling write는 사용하지 않는다. 상세 근거·SQL은
[upstream PostgreSQL 운영 문서](../deploying/container.md#postgresql-production-settings)를 따른다.

1. 운영 DB snapshot/백업을 별도 staging에 복원한다. 0.9 startup migration, 기존 response 조회,
   `previous_response_id`, conversation continuation, 동시 요청 및 재시작 후 보존을 검증한다.
2. 다음 duplicate 조회 결과가 없는지 확인한다. 데이터 제거/보정은 운영 retention 정책에 따라 별도 결정한다.
3. maintenance window에서 inbound를 중지하고 기존 replicas를 drain한 뒤 모두 0으로 내린다.
4. 최종 백업을 확인하고 0.9 한 replica를 기동한다. migration/readiness 성공 이후 새 replicas만 늘린다.
5. 초기 400, 정상 SSE, round 1+ 오류, 저장 및 continuation 검증 후 traffic을 다시 연다.

```sql
SELECT conversation_id, seq, COUNT(*)
FROM items
WHERE conversation_id IS NOT NULL AND seq IS NOT NULL
GROUP BY conversation_id, seq
HAVING COUNT(*) > 1;
```

0.9은 timestamp/sequence를 BIGINT로 확대하고 sequence index를 unique로 재구축한다. migration 실패는
기동 실패로 처리된다. DB 크기/lock 대기 기준으로 `POSTGRES_MIGRATION_TIMEOUT_SECONDS`를 조정한다.
문제 발생 시 새 replicas를 먼저 drain한다. 구버전 이미지와 업그레이드된 DB 조합을 검증 없이 바로 재사용하지
말고, staging에서 검증한 롤백 절차 또는 백업 복원을 따른다.

## 검증 범위

`responses_custom_test`는 mock HTTP upstream을 실제 gateway router에 연결하여 다음을 검증한다.

- 초기 400/404/429/503 상태와 retry/request ID headers 보존.
- 초기 upstream 성공 headers만으로 stream 반환, 지연된 첫 body를 기다리지 않음.
- unsupported grammar tool의 사전 오류.
- EOF / `[DONE]` / malformed data / generic error의 실패 및 오류 로그.
- failed/incomplete terminal의 보존 및 WARN.
- pass-through 원문 bytes 보존 및 context 오류 로그.
- unpolled stream drop 시 worker 중단, 명시적 terminal 이후 열린 upstream 연결을 기다리지 않고 종료.
- 실제 gateway web search loop의 round 1 HTTP 400 → outer 200 SSE error, round/status/category 로깅.

기존 Rust/HTTP/WebSocket/cassette 회귀 테스트도 실행한다. 실제 GPU inference 및 운영 PostgreSQL 데이터
마이그레이션은 해당 환경에서 추가 검증해야 한다.
